## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`AppServices.init(modelContainer:)` currently constructs services and immediately performs runtime side effects: generating/writing the MCP token in non-MAS builds, starting the local HTTP server, requeueing launch-time LLM work, registering a notification observer, and running availability checks. Any launch mode that needs the service graph also receives these side effects, which has already leaked into fixture generation and makes tests/previews harder to isolate.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Constructing the app service graph does not start the HTTP server, generate/write MCP tokens, run queue recovery, register launch observers, or run availability checks.
- [x] #2 Runtime side effects are started by an explicit lifecycle method or owner that takes a launch/runtime mode.
- [x] #3 Production launch still starts the expected runtime services exactly once.
- [x] #4 Fixture generation, UI-test setup, and other non-production modes can opt out of user-machine side effects.
- [x] #5 Add focused coverage or lifecycle tests that would fail if service construction alone starts runtime side effects.
<!-- AC:END -->

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
AppServices.init now constructs the service graph only — it no longer starts the HTTP server, generates/writes the MCP token, runs queue recovery, registers the availability observer, or runs availability checks (AC#1). Those side effects moved to an explicit AppServices.startRuntime() (AC#2), which the launch owner (JobhuntApp) calls only for interactive modes (plan.runsRuntimeServices) — production runs them exactly once (AC#3). The MCP token is generated by JobhuntApp gated by plan.needsMCPToken (DMG-only) and passed into init, so construction writes nothing to the machine. Fixture generation now opts out of all runtime side effects — it seeds and exits without starting a server (AC#4), closing the leak the task cites. Coverage: LaunchModeTests.testFixtureGenerateOptsOutOfRuntimeServicesAndToken and testInteractiveModesRunRuntimeServices assert the mode→startRuntime/token decisions that would fail if construction-vs-runtime separation regressed (AC#5 — the pure plan derivations are the testable seam; the @main App init/startRuntime wiring itself isn't unit-testable). NOTE: production launch/server start not runtime-verified here (no GUI session) — recommend a manual smoke launch + AppUITests before release.
<!-- SECTION:FINAL_SUMMARY:END -->
